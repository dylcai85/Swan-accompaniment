# Plan: milestones, gates, and risks

Facts about the source file (`swan.mid`, from MFiles, type 1, PPQ 256, 6/4, G major): 4 tracks. Track 0 is the tempo map (44 tempo changes, ~50-70 bpm). Track 1 is Cello (113 notes, E3-D5, monophonic once the parser clips 60 legato overlaps of 2-15 ticks, enters at bar 2 after a one-bar piano intro). Track 2 is Piano 1 (919 notes, rippling sixteenths, A1-E7, 1 onset off the sixteenth grid). Track 3 is Piano 2 (258 notes, rolled chords and bass; 50 onsets are off the sixteenth grid). 28 bars (the cello ends in bar 26; the final piano chord starts in bar 28), ~145 s at the file's tempos. Verified against the file in M1; pitches spot-checked by Dylan against the printed score.

## Setup that only Dylan can do (once)

1. Create the GitHub repo and connect it at claude.ai/code. Because no third-party score is committed (see "Local-only files"), the repo can be public (GitHub Pages is free) or private (Pages on private repos needs a paid plan, as far as I know; check).
2. Repo Settings -> Pages -> Source: **GitHub Actions**.
3. Have wired headphones ready for live tests.
4. In each cloud session that needs the real score, attach `swan.mid` (it is not in the repo) and have it placed at `local/swan.mid`.

Everything else is done by Claude Code.

## Local-only files (gitignored, never committed)

- `local/swan.mid`: the Swan MIDI (third-party). Also `local/swan-score.pdf` for the M1 spot check.
- `fixtures/synthetic/`: audio generated from the real score.
- Anything under `docs/reference/`.
- Gitignore patterns: `*.mid`, `*.midi`, `*.mxl`, `*.musicxml`, `local/`, `docs/reference/`, `fixtures/synthetic/`, `fixtures/derived/`. The one exception is the original, made-up `tests/fixtures/mini-score.mid` (un-ignore it explicitly with `!tests/fixtures/mini-score.mid`).

## Milestones

Work is committed directly to `main`; each milestone ends with an entry in `docs/MILESTONES.md`. Each milestone lists what ships, how it is verified without a mic, and what Dylan tests live.

### M0: Scaffold and deploy
- Vite + TS + Vitest + Playwright; `CLAUDE.md` commands all work; CI workflow (typecheck, test, build, e2e) on pushes; Pages deploy workflow on `main`; correct Vite `base`.
- Page with a Start button, a "headphones required" notice, and a build/version stamp.
- **Verify:** CI green; deployed URL loads; the production build serves under the Pages base path.
- **Dylan test:** open the deployed URL and confirm it loads.

### M1: Score model
- Parse the MIDI into a `Score` object: cello notes, piano 1 and piano 2 events, ticks, bar/beat positions, nominal tempo (median of tempo events). `npm run score:inspect` prints a bar-by-bar table (bar number, cello notes, piano event counts).
- Score loaded **only** through a runtime file-picker input, cached in IndexedDB, with a visible "score loaded: name, bars, note counts" status. Nothing is bundled. Also commit a tiny original `tests/fixtures/mini-score.mid` (generated by a script) so tests and CI run without the real score.
- **Verify:** tests assert 113 / 919 / 258 notes, cello first onset = bar 2 beat 1, 28 bars, all cello onsets on the sixteenth grid.
- **Dylan test:** compare the printed cello table against the PDF for ~5 bars spread through the piece (start, middle, end). Report any wrong pitch or octave.

### M2: Piano playback engine (no mic)
- Own score clock + lookahead scheduler + Tone Sampler (Salamander) + simple reverb. Controls: play/pause, seek to bar, rate slider (0.5x to 1.5x), Piano 2 on/off.
- Live rate changes reschedule unplayed notes with no glitches, no doubled notes, no dropped notes.
- **Verify:** scheduler unit tests with a fake clock (note times vs rate); an `OfflineAudioContext` test renders 10 s with a rate change and checks note onset times.
- **Dylan test:** does the piano sound acceptable (dry? choppy? needs pedal/reverb)? Drag the rate slider during playback: is it smooth? Piano 2 on/off: which do you prefer?

### M3: Mic input and pitch tracker
- Mic selection dropdown, level meter, AudioWorklet frame capture, pure-TS pitch tracker (YIN or McLeod, parabolic interpolation, confidence, median smoothing), live display of note name + cents + confidence.
- Reports `AudioContext.baseLatency` / `outputLatency` in the UI.
- **Verify:** unit tests: pitch accuracy within 10 cents on synthetic tones from 130 Hz to 600 Hz; stable under 5-6 Hz vibrato of +/-30 cents; octave-error rate under a threshold on synthetic sawtooth with harmonics; silence returns "unvoiced".
- **Dylan test:** play open strings and a slow scale. Does the displayed note match? Any octave jumps? Does it track through vibrato and slow slides?

### M4: Fixtures and eval harness
- `tools/synth-performer.ts`: render the cello part to audio with configurable tempo curve (steady, gradual accel/rit, abrupt rubato), vibrato, bow noise, and added room noise; outputs audio plus exact ground-truth note times. These are generated, not committed.
- In-app **Record take** button (uses the same mic chain as live use) that saves a FLAC/WAV download, so Dylan's takes go through the real pipeline.
- Offline DTW aligner producing reference alignment for real takes; `npm run eval` runs the follower over every fixture and prints metrics (see Gates).
- **Verify:** harness runs end to end on synthetic fixtures with a trivial baseline follower.
- **Dylan test:** record the takes listed under "Recordings needed" and commit them to `fixtures/real/`.

### M5: Score follower (offline-first, then causal)
- Frame-level probabilistic follower (HMM or equivalent): states are cello notes; observation is pitch vs expected note (relative to estimated tuning offset), voicing, and onset/energy cues (needed for repeated notes). Left-to-right transitions with stay/advance/skip, bounded window around the current estimate, relocalization after sustained mismatch. Outputs position (fractional ticks), confidence, and tempo `rate`.
- Must be strictly causal (uses only past audio) and run faster than real time.
- **Verify:** `npm run eval` gates below on synthetic and real fixtures.
- **Dylan test:** none beyond fixtures (the closed loop comes in M6).

### M6: Closed loop
- Connect follower to the score clock (smooth convergence, no jumps), plus the session state machine: IDLE -> COUNT_IN -> FREE_RUN (piano plays bar 1 at the chosen starting tempo) -> FOLLOWING -> HOLD (cello silent: keep last rate) -> LOST (low confidence: keep last rate, don't jump) -> END.
- Start tempo slider and count-in click. Debug overlay: cello position, piano position, rate, confidence, state.
- Fake-mic e2e test: feed the synthetic take, assert that the piano position tracks within gates.
- **Dylan test:** the first real live run. Play the Swan from the top with headphones. Report: does the piano enter well, does it follow slowing/speeding, what happens when you make a mistake, and does it feel late or early?

### M7: Calibration and polish
- Output-latency calibration (tap-to-click test or manual offset slider) and forward-prediction compensation; tuning-offset display; piano dynamics following cello loudness; Start-from-bar; tidy UI.
- **Dylan test:** repeat M6 and compare. Is the sync tighter after calibration?

### M8 (stretch): Beyond the Swan
- Load any MIDI as the score with a track picker (cello part vs accompaniment tracks); MusicXML import; test on a second piece with long solo rests and a larger accompaniment texture. YouTube/recorded-audio accompaniment stays parked unless a legitimately processable audio source is chosen.

## Gates (starting targets; tune them with data, but keep them explicit)

Measured by `npm run eval` at cello note onsets after the follower has locked:
- Median absolute alignment error <= 60 ms; p95 <= 150 ms.
- Zero false LOST states on clean fixtures.
- After a deliberate mistake (wrong note and a one-bar pause), re-lock within 2 s of the cello resuming.
- Works across tempo curves: steady, +/-25% gradual, and abrupt ritardando to 60% speed.
- Runs at least 10x faster than real time in Node.
Report the full table in the commit and `docs/MILESTONES.md` for every change that touches follower or pitch code. Regressions must be fixed before pushing.

## Risks and open questions (pressure test)

1. **Piano bleed into the mic (blocker for speaker use).** If the piano plays through speakers, the mic hears it and the follower gets confused; the Swan's piano shares pitches with the cello line, so it cannot be filtered out. Mitigation: headphones are required for the MVP (wired; one earbud out is fine). Speaker mode is a stretch goal needing echo cancellation against the known piano signal.
2. **Third-party score and cloud sessions.** The MIDI is third-party and its license is unverified, so it stays local and out of git. Consequences: the deployed app must load the score via a file picker; cloud sessions and CI start without the real score, so tests need a committed mini score and real-score tests must skip when it is absent; each cloud session that needs the real piece needs `swan.mid` attached again. Real-score eval can only run in such sessions or on Dylan's machine. Never commit the file even once (history keeps it). Also remember: a public repo means any committed recordings of Dylan are public; keep them in `local/` if that's unwanted.
3. **The start problem.** There is no cello sound in bar 1, so the app has no tempo information. The piano must start itself (count-in at a chosen tempo) and free-run until the cello enters, then adapt. Define this behavior in M6, not as an afterthought.
4. **Latency is the real-time budget.** Mic input + analysis window (~40-50 ms for low notes) + output latency. Bluetooth headphones add 150-300 ms and often degrade the mic: do not use them. Compensate by predicting forward by the measured latency (M7). The Swan's slow legato line makes ~50-100 ms of residual lag tolerable.
5. **Cello pitch tracking is harder than it looks.** Vibrato, slides, bow-change noise, octave errors, and legato passages with no amplitude onset. Repeated same-pitch notes cannot be separated by pitch alone, so onset/energy cues are required.
6. **Tuning.** If the cello isn't at A=440 the pitch match drifts near semitone boundaries. Estimate and apply a global offset.
7. **Synthetic audio is not a real cello.** Synthetic tests prove the plumbing, not the musical result. The real takes and live tests are the true acceptance; plan for iteration after M6.
8. **Piano sound quality.** The MIDI is likely flat (no pedal, uniform velocity), so raw playback will sound dry. Reverb in M2, dynamics-following in M7, and optionally sustain-pedal heuristics.
9. **Authored rubato in the MIDI.** The embedded tempo map must not leak into the follower's expectations (see CLAUDE.md). Optionally use it later as a prior for where phrases slow down.
10. **Browser support.** Develop for desktop Chrome/Edge first. Safari and iOS have AudioWorklet and autoplay quirks; mobile is out of scope until M8.
11. **Dev loop.** Cloud sessions can't hear anything, so each milestone ends in a Dylan test on the deployed site. Keep milestones small so feedback arrives quickly.
12. **Score accuracy.** The MIDI is only trusted after the M1 PDF spot check. A wrong reference note will look like a follower bug.
